# ADR-02: issue 実装ループの検証・整形コマンド

- **日付**: 2026-07-21
- **ステータス**: 採用
- **対象**: ADR-01 の issue 実装遂行フェーズにおいて、1 つの issue を実装するときに使う検証・整形コマンドを固定する。

## 背景・課題

ADR-01 で issue のライフサイクル（起票 → open/closed）は決めたが、「1 つの issue を実装するときに何を実行して緑を確認するか」は決めていなかった。毎回 `Makefile` や `.golangci.yml` などのツール構成を探索するのはコストであり、コマンドを固定しておけば探索なしで即着手できる。

## 決定

### 1. 検証は直叩きに固定する（構成ファイルを探索しない）

- テスト: `go test ./...`
- lint: `go vet ./...`（`golangci-lint` 等の追加 linter は使わない）
- ビルド確認が要るとき: `go build ./...`
- `Makefile` / スクリプト / `.golangci.yml` などの有無は確認しない。上記コマンドを直接使う。

### 2. 整形（gofmt）

- `gofmt -l -w .` はいつ実行してもよい（実装の途中でも、`go vet` の前でも可）。
- ただし**コミット直前には必ず実行する**。

### 3. コミット

- コミット・PR はユーザーが明示的に求めたときのみ行う。その直前に gofmt を実行する。

### 4. 実装中の非自明な発見は `docs/02notice.md` に追記する

ADR-01 は `docs/02notice.md` を「実装しながらの気づきの蓄積ログ」と位置づけているが、本 ADR の検証ループにはその記録手順が組み込まれておらず、書き忘れが起きやすかった。そこで検証ループの一手順として明示する。

- 「非自明」の判定基準（リトマス試験紙）: **issue ファイル本文・AGENTS.md・既存の ADR/DEC だけを読んで、追加の grep・Read・実行なしにその答えに辿り着けたか？** 辿り着けなかったものだけが対象になる。該当しうる例:
  - 外部ライブラリ・ツールの実際の挙動（ソースを読む・`go doc` を引く・実行して初めて確定したもの）
  - 確定済みの DEC/FR/issue 本文を実装しようとして初めて露見した、ドキュメント側に書かれていないギャップ（責務の境界、型の表現力不足など）
  - 実装・テストで踏んだ API 上の落とし穴（気づかないと静かに壊れる・無効化されるもの）
  - 既存テストのカバレッジの非対称性・抜け穴（再読して初めて気づいたもの）
- 記録先は issue ファイル自体ではなく `docs/02notice.md` にする。issue は `closed/` へ移動されると `docs/issues/README.md` の open 一覧から外れ、他の issue を実装する際に見に行かれるとは限らないため。
- `docs/02notice.md` は整理されたストック情報ではなく、ラウンドを追記していくフロー情報として扱う。過去の記述の構成見直しは行わなくてよい（実害が出るまで後回しでよい）。

## 結果

1 つの issue を回す開発ループは次に固定される:

1. issue 選定（`docs/issues/README.md` から open を 1 件）
2. 現状把握（`git status` / 関連コード確認）
3. 実装
4. 検証ループ（緑になるまで）: `go build ./...` / `go vet ./...` / `go test ./...`
5. 実装中に非自明な発見（上記リトマス試験紙に該当するもの）があれば `docs/02notice.md` に追記
6. コミット前のみ: `gofmt -l -w .`（コミットは求められたときだけ）
