# ADR-00: ドラフト作業の進め方（draft.md / 02notice.md / 01decision(.pre).md ループ）

- **日付**: 2026-07-21
- **ステータス**: 採用（第2回以降、継続運用中）
- **対象**: `docs/00origin.md`（機能仕様）を実装に落とし込む過程で、設計原則・パッケージレイヤ構成レベルの未決事項を洗い出すための作業手順そのもの。

## 背景・課題

`docs/00origin.md`は「何を提供するか」（機能仕様）を定めているが、「どう実装するか」（設計原則・パッケージ構成・コーディング規約）は会話の中で確認しながら`docs/01decision.md`に確定させていく必要がある。この確定作業を、実装に着手する前にどう進めるかについて、当初のやり方（第1回）がユーザーの意図と合わず、方針転換（第2回）した経緯がある。

## 第1回で試みて却下されたやり方

最初は`internal/config`という1パッケージを実際にビルド・vetが通るところまで丁寧に作り込み、そこで見つかった細かい仕様の揺れ（`Load`のエラー処理、ファイルパーミッションビット等）を質問にする、というやり方を試みた。

これはユーザーから「求めていたものと違う」という指摘を受けて却下された。理由: 決めたかったのは特定パッケージの実装詳細ではなく、**設計原則・コーディング原則**、および「実際に手を動かして初めて発覚する、パッケージ間の繋がり方の未決事項」だったため。1パッケージを深掘りするアプローチでは、この種の発見が得られない。

## 採用した進め方（第2回以降）

### 1. `docs/draft.md` — repomix風の全体俯瞰スケッチ

- 1パッケージを丁寧に作り込むのではなく、**リポジトリ全体**（`go.mod` 〜 `cmd/` 〜 `internal/*` の各パッケージ）を、1つのファイルにrepomix的（＝複数の疑似ファイルをパス見出し付きで連結する形式）にラフへ書き通す。
- 各コードフラグメントには、確信度タグをインラインで付す:
  - `[検証済み]`: 実際に`go build`/`go vet`/`go doc`等で動作・実在を確認したもの。
  - `[未検証]`: 標準的なAPIの使い方として妥当と思われるが、実際に組んで動かしてはいないもの。
  - `[設計上の仮定]`: ここで初めて「こうであるはず」と勝手に置いた設計判断。次節の質問の元ネタになる。
- 目的は個々の実装の正しさではなく、**設計原則・パッケージレイヤ構成レベルの未決事項**（共有ドメイン型の置き場所、パッケージ間の依存の向き、副作用の境界、データの受け渡し方等）を掘り当てること。個々の関数のちょっとした挙動（エラーメッセージの文言、ファイルパーミッション等）は意図的に扱わない。
- Go APIの実在・シグネチャは、可能な限り`go doc`や使い捨てモジュールでの実際のビルド・vet実行によって裏取りし、確信度タグに正直に反映する。

### 2. `docs/02notice.md` — 気づきの蓄積ログ

- ドラフトを書く各回（第1回、第2回、…）で気づいたこと・技術的発見・方針転換の経緯を、**追記のみ**（上書きしない）で蓄積する。
- 「なぜこの設計にしたのか」ではなく「書いてみて何が分かったか」を記録する場であり、確定事項そのものは書かない（確定事項は`01decision.md`側の責務）。
- PRE項目の根拠になる事実・ケース分類・実験結果も、まず本書に書く。`01decision.pre.md`は確認用の問いを置く場所であり、調査ログの本文を抱え込ませない。

### 3. `docs/01decision.pre.md` — 未決事項の一時置き場

- その回のドラフト作業で見つかった、**設計原則レベル**の未決事項だけを`PRE-N`として列挙する。個別関数の細かい挙動は対象外（第1回の反省）。
- 各質問には「推奨（デフォルト）」を実装者側の提案として添えるが、これはユーザー確認が済むまで確定事項（`DEC-`）にはしない。
- 各PREは、原則として「質問」「推奨（デフォルト）」「理由」「確認後の反映先」の形に要約する。長い事実列挙・ケース表・実験ログは`docs/02notice.md`へ逃がし、PRE側にはユーザーが何を判断すればよいかだけを残す。
- ユーザーへの確認は、質問UI（`AskUserQuestion`等）でデフォルト＝推奨案とした選択肢を提示する形で行う。
- 確認が済んだ項目は本書から削除し、`docs/01decision.md`に`DEC-`として追記する（`PRE-N` → `DEC-11.N`のように対応関係が追える形にする）。ユーザーが推奨デフォルトと異なる判断をした場合は、その理由も`DEC-`側に記録する。
- ADR本文の運用ルール自体が曖昧だと分かった場合は、PRE項目に無理に運用解釈を書き足すのではなく、該当ADRをその場で最小限更新して以後の判断基準を明確にする。

### 4. `docs/01decision.md` — 確定済み決定の自己完結した記録

- 一度確定した`DEC-`は、明示的な理由がない限りそのまま実装のベースラインとしてよい記録として蓄積する。
- バージョン履歴（v1.0、v1.1、…）として、どの回のドラフト作業で何が確定したかを冒頭にまとめる。

### ループの回し方

```
docs/draft.md を書く／深掘りする
   → 設計原則レベルの未決事項が見つかる
   → docs/01decision.pre.md に PRE-N として整理（推奨デフォルト付き）
   → ユーザーに質問UIで確認（デフォルト＝推奨案）
   → 回答を docs/01decision.md に DEC-11.N として追記、01decision.pre.md から削除
   → docs/02notice.md に「今回気づいたこと」を追記
   → 確定した原則を docs/draft.md に反映し、もう一段深く書いてみる（次回へ）
```

このループを、新たな原則レベルの未決事項が出てこなくなるまで繰り返す。実装しながらでないと決められない種類の事項（例: テストハーネスの具体的な構成・golden再生成の手段。`DEC-7.5`参照）は、ここでのヒアリング対象にはせず、実装着手後の試作・実験に委ねる。

## 判断基準: 何を質問にし、何を質問にしないか

- **質問にする**: 後から変更するとコストが大きい、パッケージ間の構造・依存方向・責務分担・共有データ型の設計。「一度書いてしまうと複数パッケージにまたがって直すのが大変」な種類の決定。
- **質問にしない**:
  - 1関数・1箇所の実装の細部（エラー文言、パーミッションビット等）。
  - 実際に手を動かしながらでないと良し悪しを判断できない事項（テストハーネスの具体的構成等）。これは`DEC-7.5`のように「実装しながら確定させる」という方針そのものを`01decision.md`に明記し、質問では扱わない。

## 結果

このやり方に転換して以降（第2回〜第4回）、`internal/model`→`internal/shape`への統合、D1のconfig読み込み方針、`internal/fix`への型情報の受け渡し方、副作用境界、エラー表現方針、テスト依存方針など、実装着手前に固めておくべき原則レベルの決定を、実際にコードを書いてみることでしか見えなかった形で数多く洗い出し、`docs/01decision.md`のDEC-11.1〜DEC-11.14として確定できた。
